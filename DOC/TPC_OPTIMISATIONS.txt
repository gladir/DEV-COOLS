OPTIMISATIONS DE TAILLE DE TPC.PAS (clone de Turbo Pascal 7, 8086 mode reel)
===========================================================================

But : produire du code aussi compact que le Turbo Pascal 7 d'origine (IO.SYS du noyau
MSDOS-0 : 65 285 octets -> 54 116 octets avec ces optimisations, TP7 : ~58 Ko).
TPC est un compilateur a une passe a modele "accumulateur" (AX, DX:AX) ; les
optimisations sont des judas (peephole) sur le code deja emis, completes par
une compilation en plusieurs passes (le code est rejoue jusqu'a stabilite).

Compilation en plusieurs passes
-------------------------------
* Passe 1 (analyse) : sauts longs, graphe d'appels. Passes suivantes : memes choix
  que la passe precedente (tableaux ShortPred/FramePred indexes par un numero
  d'ordre de saut ou de routine), jusqu'a stabilite (au plus 10 passes) ;
  une prediction fausse force l'option "long" au tour suivant ; filet de
  securite : derniere passe sans optimisation par prediction.
* Variables d'environnement de mise au point : TPC_NOJ, TPC_NOIF, TPC_NOBACK
  (pas de sauts courts "jmp", "jcc", arriere), TPC_KEEPES (sauvegarde ES autour
  des appels), TPC_NOSMART (pas d'edition de liens intelligente),
  TPC_PASSES (nombre de passes), TPC_SHOWDEAD (routines retirees),
  TPC_SIZES (taille de chaque routine).

Sauts
-----
* jmp/jcc rel8 quand la cible est a moins de 120 octets (conditionnels : le motif
  "jcc inverse +3 ; jmp cible" (5 octets) devient "jcc cible" (2 octets)).
* Saut arriere court immediat ; la sequence "jcc +n" ecrite a la main n'est jamais
  suivie d'un saut raccourci (AfterSkip) ; le runtime ecrit a la main reste long.
* Inversion directe : comparaison suivie de "mov ax,1 / jcc / xor ax,ax" ->
  saut conditionnel direct ; "not b" -> saut inverse (pas de "xor ax,1").

Acces aux variables
-------------------
* Variables scalaires de la frame : "mov ax,[bp+d]" / "mov [bp+d],ax" au lieu de
  "lea di,[bp+d] ; push ss ; pop es ; es: mov ax,[di]" (idem pour les
  champs : le deplacement d'un champ est replie dans d).
* Tableaux locaux indexes : "mov di,ax ; lea di,[bp+di+d]" (acces direct
  [bp+di+d] pour les lectures).
* "add di,imm" replie dans l'acces final : "es: mov ax,[di+imm]".
* Constantes : "mov word [bp+d],imm", "mov byte [bp+d],imm", "es: mov byte
  [di+d],imm" ; resultat constant d'une fonction : "mov ax,imm".
* Operandes memoire : "add/sub/or/xor/and/cmp ax,[bp+d]", "imul word [bp+d]",
  "cmp al,[bp+d]" (char/bool/enum) a la place de "push ax ; mov ax,[bp+d] ; mov bx,ax ; pop ax ; op ax,bx".
* Tests de booleens/comparaisons avec constantes : "cmp byte/word [bp+d],imm" dans
  les conditions de if/while/repeat.
* Parametres valeur : "push [bp+d]" (mot, longint, octet).
* Variable de boucle FOR : "inc/dec [bp+d]" ; borne dans la frame ("cmp ax,[bp+d]")
  au lieu de la pile ("mov bx,sp ; cmp ax,[ss:bx]" + "add sp,2" en sortie).

Arithmetique
------------
* Division/modulo par une constante non nulle : pas de test de zero ni de debordement ;
  puissances de 2 non signees : shr / and ; multiplication par 2^k : shl ; sinon "mov bx,imm".
* Les operations utilisent "mov bx,imm" a la place de push/mov/pop.

Fonctions et frames
-------------------
* Le stockage du resultat juste avant l'epilogue est supprime (la frame disparait) ;
  une fonction qui s'acheve par une constante : "mov ax,imm".
* Frame sans variable locale : ni "sub sp,0" ni "mov sp,bp" (prediction multi-passes
  si aucune boucle FOR sur la pile n'est active).
* ES n'est plus sauvegarde autour des appels utilisateur (ES est volatile).
* Plus de "xor ah,ah" double apres un chargement d'octet.

Donnees
-------
* Chaines litterales identiques partagees (dans la meme unite).
* StringArg255 / StringAssign255 : appel sans mots en ligne pour string[255].
* Write/WriteLn d'une chaine du segment de donnees (litterale ou variable globale) : "mov ax,imm16 ; call RuntimeString"
  (le push ds / mov ds,dx / pop ds et le mov dx,ds sont supprimes : DS est deja le segment de donnees),
  6 octets de moins par instruction ; COMMAND.PAS gagne ~2 Ko.

Edition de liens
----------------
* Edition de liens intelligente par defaut (comme TP7) : les routines jamais
  appelees (graphe d'appels, racines : programme, initialisations d'unites,
  crochet CRT) ne sont pas liees. Obligatoire quand le segment de code deborde.

Correction de comportement (pas une optimisation)
-------------------------------------------------
* Un produit de constantes entieres qui deborde 16 bits (30*4096) devient une constante Longint (122880) au lieu d'etre
  tronque a 16 bits (-8192), comme Turbo Pascal 7.

Code de plus de 64 Ko : mode multi-segments
-------------------------------------------
Un EXE MZ de TPC n'avait qu'un seul segment de code (65 520 octets, erreur 48 au-dela). Quand le code deborde
apres l'edition de liens intelligente, TPC bascule automatiquement en mode multi-segments, comme TP 7 qui
place chaque unite dans son propre segment ; les programmes qui tiennent dans 64 Ko produisent exactement les
memes EXE qu'avant (le mode n'est jamais active pour eux).
* Detection : la passe d'analyse deborde (Overflowed) ; apres SmartLink, si une passe deborde encore, le mode
  est active et les passes reprennent a zero. Variables d'environnement : TPC_NOMULTI (desactive le mode, erreur 48
  comme avant), TPC_SEGSIZE=n (force le mode, segments d'environ n octets, 2000..65504, pour essayer le
  mecanisme sur de petits programmes), TPC_SIZES (taille et segment de chaque routine, taille de chaque segment),
  TPC_PASSES (detail des passes).
* Routines : toute routine globale (non imbriquee) devient FAR : retour RETF, appel "PUSH CS ; CALL near" dans le
  segment de la routine, "CALL FAR seg:off" vers un autre segment (segment relocalise par la table MZ, kind 8+n ;
  une routine pas encore definie est resolue a l'edition de liens par CodeRefs). Les routines imbriquees restent
  NEAR dans le segment de leur parent. @Proc, Ofs/Seg, adresses en assembleur : offset et segment de la routine
  visee. Blocs d'initialisation d'unites : RETF, appeles par le segment du corps principal. Crochet de sortie de
  Crt (CrtHook) : pointeur FAR de 4 octets, appele par "CALL FAR [hook]". Le demarrage (segment 0) saute au corps
  principal par un JMP FAR.
* Repartition (une seule passe) : le code est compile une fois ; avant chaque routine globale, si sa taille (mesuree
  a la passe precedente, plus 6 % + 32 octets) ne tient plus dans le segment courant, le segment est ferme et un
  nouveau commence par une copie du runtime (octets 0..RuntimeEnd-1, avec leurs fixups de donnees et
  relocalisations : memes decalages dans chaque segment, donc les appels proches vers le runtime, StackCheck et
  StringArg lisant leurs mots en ligne, fonctionnent partout). Pas de changement de segment dans le code qui
  declenche la compilation du runtime Real (SegDepth). Un segment trop petit (SegTooBig) augmente la marge
  (SegReserve) et refait une passe. Les donnees (un seul segment, DS) ne sont jamais dupliquees.
* Edition de liens (MultiSegLoad / WriteExecutable) : segments a des frontieres de paragraphe consecutives,
  fixups de donnees appliques a chaque segment (FinalDataAddress), relocalisations MZ rebasees, puis les donnees.
  Les erreurs d'execution affichent le segment du code ("Erreur d'execution 200 a 07D8:1C28." : CS - PSP - 16).
* Limites : pas d'unites TPU natives Borland, d'OBJ ($L), d'overlays, de map (-G) ni d'infos de debogage dans
  l'EXE dans ce mode (erreur 48 explicite) ; les TPU des unites sources ne sont pas ecrits ; au plus 32 segments ;
  une routine globale ne peut pas depasser un segment ; les adresses de debogage sont relatives a leur segment.
* Tests : TESTS/TPC_MULTISEG/run_tests.sh (MSDOS0=chemin pour FDISK, FORMAT et LINK de MSDOS-0).
* Validation : FDISK, FORMAT et LINK de MSDOS-0 (88,9 / 87,5 / 99,5 Ko de code, 2 segments) s'executent comme les
  binaires de reference (FDISK : memes ecrans que BIN16/FDISK.EXE ; LINK : memes EXE et MAP qu'une version Free Pascal
  native) ; les 27 programmes de la racine qui echouaient en erreur 48 (MASM, LUA86, AWK86, REXX86, QPDF... jusqu'a
  225 Ko de code, 4 segments) compilent et leurs sorties sont identiques a celles de leur version native ; les 263
  autres programmes de la racine et 53 de MSDOS-0 donnent des EXE octet pour octet identiques a ceux d'avant.
* Defaut latent (non corrige en mode normal pour garder des EXE identiques) : JumpZero fusionne une comparaison
  booleenne quand CondTail=CodeSize ; CondTail n'etait pas invalidee apres usage, et une valeur perimee pouvait
  coincider plus tard avec CodeSize (un appel FAR de 9 octets remplacant une sequence de meme longueur) et faire
  retirer 7 octets d'un code sans rapport. En mode multi-segments, toute emission invalide CondTail.
* Segment de donnees (FASTOPEN.PAS, erreur 49) : le programme declare 64 055 octets de globaux (tableau de
  TDriveCache 63 778 + 277), mais TPC ajoute ~5,6 Ko de donnees de runtime (anneau de chaines 2 048 + brouillons 512
  alloues meme sans fonction chaine, tables d'overlays 1 330 meme sans l'unite Overlay, TextRec Input/Output 512,
  litteraux en DS au lieu du segment de code de TP7...) : 69 609 octets au total pour 65 520 permis. Meme sans les
  tables d'overlays ni l'anneau, il resterait environ 200 octets de trop : non corrige.
