JSCW32 - Compilateur JavaScript vers executable Windows 32 bits (80386)
=======================================================================

Syntaxe
-------
  jscw32 [options] fichier.js

Produits
--------
  Par defaut : fichier.exe (PE32 console, KERNEL32.dll).
  -obj       : fichier.obj seulement (COFF i386, pas d'edition de liens).
  -asm       : ecrit en plus fichier.asm (syntaxe NASM Win32 : nasm -f win32).
               Le .asm n'est jamais ecrit sans -asm.
  -o nom     : nom de base commun (nom.exe / nom.obj / nom.asm).
  Un ancien .exe est supprime avant une nouvelle production en mode EXE.

Pipeline
--------
  .js -> jetons -> AST -> analyse semantique -> IR 80386 -> [.asm] -> .obj COFF
      -> .exe PE32. Le formateur de console (inspect de Node) est un prelude JS
  ajoute a la fin du source ; les lignes du programme gardent leur numero.

Execution et diagnostics
------------------------
  -run       execute le programme dans l'emulateur 80386 integre (pas besoin
             de Windows). -v, -tokens, -ast, -scopes, -runtime, -data, -ir,
             -rt (avec -ir) affichent les etapes internes.

Harnais de validation (-test)
-----------------------------
  jscw32 -test [dossier] [-obj] [-asm] [-keep]

  Compile chaque .js du dossier (SAMPLES\JS par defaut) dans un sous-processus
  et verifie :
    mode EXE     (defaut)  : en-tetes MZ/PE du .exe, puis execution ;
    mode OBJ     (-obj)    : en-tete COFF i386 du .obj ;
    mode ASM+OBJ (-asm -obj) : .asm et .obj.
  Execution : sous Windows le .exe est lance ; ailleurs, si la variable
  d'environnement JSCW32_RUNNER est definie (par exemple JSCW32_RUNNER=wine),
  le .exe est lance avec cette commande ; sinon l'emulateur integre (-run) tient
  lieu d'execution. La sortie est comparee aux commentaires
  « // attendu : valeur » du source, dans l'ordre :
    « a puis b »   deux lignes a et b ;
    « a, b, c »    trois lignes consecutives ;
    « v (texte) »  la parenthese finale est un commentaire ;
    « Error: v »   une ligne d'erreur correspond a v.
  Sans commentaire « attendu », le test exige une compilation et une execution
  sans erreur. test11adv se termine volontairement par une exception non
  rattrapee (instanceof sur un objet) : c'est le resultat attendu.
  Les artefacts jt_* sont supprimes (sauf -keep). Le code de sortie est 1 si
  au moins un fichier echoue.

Limites connues
---------------
  - Aucune table interne n'a de taille fixe : source, jetons, AST, symboles,
    portees, pool de donnees, instructions, tampons COFF/PE et sorties du
    harnais sont des listes chainees par blocs allouees sur le tas (bloc de
    32 Ko, curseur sur le dernier bloc utilise). Seules la memoire disponible
    et l'espace d'adressage de l'emulateur -run (64 Mo, memoire simulee d'une
    machine) bornent la taille d'un programme. Restent fixes par nature :
    les registres et la pile FPU de l'emulateur, les 4 sections COFF, les
    tables constantes (mots-cles, operateurs, prelude) et les tampons de
    lecture de fichier.
  - Chaines : le texte est stocke en UTF-8 (WTF-8 pour les demi-paires isolees)
    mais length, les indices, charAt, charCodeAt, slice, substring, indexOf,
    split(''), les iterateurs et les expressions regulieres comptent des
    unites UTF-16, comme Node ('e accent'.length vaut 1, un emoji vaut 2). Les
    chaines ASCII gardent un chemin rapide sans conversion. toUpperCase et
    toLowerCase suivent les tables Unicode (� devient SS, sigma final...) ;
    localeCompare et normalize sont des approximations (pas de tables
    de collation ni de decomposition complete). Une demi-paire isolee peut
    exister dans une chaine mais est ecrite U+FFFD en sortie ; chercher une
    demi-paire isolee avec indexOf ne la retrouve pas toujours.
  - Ramasse-miettes : marquage et balayage conservatif, sans deplacement, qui
    se declenche tous les 8 Mo alloues (puis autant que la memoire vivante).
    Les racines sont les piles, les registres et la section .data ; un
    entier ou un double qui ressemble a une adresse de tas peut retenir une
    cellule a tort (jamais l'inverse). WeakMap et WeakSet tiennent leurs cles
    fortement ; il n'y a ni finaliseur ni WeakRef. Les grands blocs sont
    rendus au systeme (VirtualFree), les pages de petites cellules sont
    reutilisees mais pas rendues. __gc(), __gcstats() ([octets vivants,
    collectes]) et __gcstress(n) (collecte tous les n octets, pour les essais)
    sont disponibles. L'emulateur -run ne reutilise pas la memoire des grands
    blocs.
  - Expressions regulieres : lookbehind, groupes nommes ((?<nom>...), \k<nom>,
    $<nom>), matchAll (iterateur), drapeau u avec \u{...} et plages hors BMP
    dans les classes sont pris en charge. Ecarts : le drapeau i ne replie la
    casse que pour l'ASCII ; pas de \p{...} ; le point (.) consomme un point
    de code entier meme sans drapeau u (Node : une unite UTF-16).
  - Classes : l'appel d'une classe sans new leve un TypeError ; super.methode()
    fonctionne dans les fleches, mais super(...) (appel du constructeur
    parent) dans une fleche n'est pas gere.
  - JSON.parse (reviver) et JSON.stringify (replacer fonction ou tableau,
    indentation) suivent Node. toFixed et l'affichage des doubles sont exacts
    (arithmetique entiere en precision arbitraire).
  - Traces de pile : � at fonction (fichier:ligne) � avec la ligne de l'appel,
    sans numero de colonne.
  - Les messages d'erreur du runtime (TypeError, RangeError... produits par le
    moteur) peuvent differer de ceux de V8.
  - Date, Map, Set, WeakMap, WeakSet, Symbol, Promise, async/await, les
    generateurs (function*, yield), BigInt, setTimeout/setInterval/
    setImmediate, require, eval, new.target, les gabarits etiquetes,
    toPrecision et toExponential sont implementes, en grande partie par un
    « prelude » JavaScript (DOC/prelude/*.js) ajoute au programme a la
    compilation. Limites de ces ajouts :
      * Date : fuseau UTC uniquement ; analyse de chaines limitee aux
        formats ISO, « Mar 5, 2021 08:09:10 » et jj/mm/aaaa.
      * async/await et generateurs : coroutines a pile propre (64 Ko) ;
        pas de generateurs asynchrones ni de « for await ».
      * BigInt : precision arbitraire (objet du prelude) ; x++ sur une
        valeur retournee par x++ devient un nombre ; 0n est « truthy » ;
        pas de Map/Set par valeur sur les BigInt.
      * new.target : variable globale positionnee par new ; une fonction
        appelee normalement depuis un constructeur peut le voir a tort.
      * require : util, assert, events, os, path (syntaxe POSIX), timers,
        timers/promises, perf_hooks, process. fs, http, crypto... lèvent
        une erreur explicite. Pas de require de fichiers relatifs.
      * eval : seulement des expressions (litteraux, operateurs, tableaux,
        objets, Math/JSON/Number/String..., appels de methodes) ; pas
        d'instructions (var, function, if...) ni d'acces aux variables du
        programme ; new Function n'existe pas.
      * Les gabarits etiquetes n'ont pas de cache par site d'appel (le
        tableau strings est recree a chaque evaluation).
  - Les .exe n'ont pas ete executes sur une machine Windows par l'auteur du
    harnais : leur validation repose sur l'emulateur, binutils, DISEXE et des
    controles de relocation.
